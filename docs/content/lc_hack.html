LC Hack

Repository Download

A hacking minigame built around a fake Linux terminal and desktops. Players read files, scan networks, hop between machines with ssh and rdp and get past firewalls until they have root access on the target machine. Passwords never leave the server.

Installation

Install all resource dependencies

  • ox_lib
  • ox_target (optional, terminals use ox_lib points with [E] without it)
  • OneSync, the server checks the player's position when a terminal is used.

Download a release or clone the source code

  • Download the latest release.
  • Or clone the repository: git clone https://github.com/LAURIDS0/lc_hack.git

Start the resource

Start lc_hack after its dependencies in your server.cfg.

ensure ox_lib
ensure ox_target
ensure lc_hack

Try it

Two test commands are included in server/commands.lua. Both require the group.admin ace.

  • /hack opens the example network on yourself.
  • /hackterminal creates a test terminal at your position.

The example is solved by reading /var/mail/alex, running ssh backup@10.0.0.12, reading /opt/backup.sh, running ssh dbadmin@db-server, reading ~/.mysql_history and finally su.

Usage

lc_hack is used from your own resources through exports. Add it as a dependency, so it always starts first.

dependencies {
    'ox_lib',
    'lc_hack',
}

Then create a terminal in the world, or start a hack directly on a player. Both take a HackConfig describing the machines.

-- A terminal players use with ox_target
exports.lc_hack:createTerminal({
    name = 'office_pc',
    coords = vec3(-1062.1, -246.0, 44.3),
    config = config,
    onSuccess = function(source)
        -- the player got root on the target
    end,
})

-- Or a hack started from your own code, e.g. an item
exports.lc_hack:startHack(source, config, function(success) end)

See Examples for complete setups.

How it works

  • Configs live on the server. The client receives a copy without password and rootPassword.
  • Every password attempt (ssh, rdp, su, sudo) is checked by the server, which also counts attempts.
  • The server decides when the player wins (root on the target) and calls your callbacks.
  • Closing a terminal pauses the hack. It is kept until the player walks away (keepDistance).
  • File contents are sent to the client so the player can read them. A cheater could read them directly, but still has to send the correct root password to the server to win.

Common Issues

Problems that come up when setting up terminals and networks, and how to solve them.

The screen is mirrored or faces the wrong way

heading is the heading of a player standing in front of the screen and looking at it, not the direction the screen faces. Stand in front of the spot, look at it and use your own heading. If the screen faces away, add 180.0.

The screen is blank or has no icons

  • Screens are DUIs created with lib.dui. Make sure ox_lib is up to date.
  • Icons and fonts are loaded from cdnjs, so the client needs internet access.
  • DUIs are only created within the screen's distance (default 15.0).

The ox_target option doesn't show

  • The zone is a sphere around coords with radius. On a screen without coords, it sits on the screen and the radius is half the screen's width.
  • The option is shown within radius + 2.5 meters. The server accepts the player within radius + 3 meters.
  • Without ox_target, terminals use ox_lib points with [E] instead.

Terminals disappear when lc_hack restarts

Terminals live in lc_hack, so a restart removes them. Create them again when lc_hack starts.

local function createTerminals()
    exports.lc_hack:createTerminal({ ... })
end

CreateThread(createTerminals)

AddEventHandler('onResourceStart', function(resource)
    if resource == 'lc_hack' then createTerminals() end
end)

The same goes for minigames registered with registerGame.

ssh or ping can't reach a machine

  • Both machines need an IP on the same /24 network. A machine on another network is only reachable from a machine with an IP on both.
  • Names like db-server only work when they are in /etc/hosts on the machine the player is on.
  • ssh needs port 22 in ports, and the firewall must allow the player's IP or open the port.
  • ssh only works with the machine's user. Other usernames, including root, are always refused.

rdp says Connection refused

The machine needs a desktop, and port 5900 in ports. Machines without ports get the right port automatically.

startHack or startGame returns false

A player can only have one hack or minigame open at a time. Check with isHacking and isPlaying.

onFail is called although the player only closed the terminal

A closed terminal is kept until the player is further away than keepDistance (default 10.0). Increase it if players need to walk further between computers.

A website shows 404 or has no styling

  • Only files that index.html links to (directly or through other pages) are loaded. Check the server console for website ... not found warnings.
  • Restart lc_hack after changing websites/ or config.lua.
  • Stylesheets and images from other sites are never loaded. Put them in the website folder.

A name like northbank.com can't be found

  • Add the name to dns in config.lua. www. names need their own entry.
  • A machine's own /etc/hosts is checked first and can point the name somewhere else.

Players can't save files on a server

  • The player has to log in to the server in that hack (ssh) with the right password.
  • The server's user can only write in its home, /tmp and /var/www/html. Root writes everywhere.

Websites players built are gone

They are saved in serverdata.json in the resource folder, which is deleted when the folder is replaced on an update. See Saved changes.

The browser test mode shows nothing

  • Run the web server in the lc_hack folder (or your resources folder) and open /web/, not the web folder itself: the test mode reads config.lua and server/commands.lua.
  • The browser console says which file it couldn't find.

Config

Resource configuration is handled in config.lua in the resource folder. It is only loaded on the server, so passwords in it never reach players. Restart the resource after changing it.

Everything in it is optional. Hacks themselves are not configured here: they are created from your own resources with exports and a HackConfig.

return {
    -- Servers that are always on: part of every hack, reachable from every machine
    servers = {
        {
            ip = '82.103.40.12',
            host = 'northbank-web',
            user = 'webadmin',
            password = 'N0rth!Web',
            rootPassword = 'Vault-2049',
            website = 'websites/northbank',
            firewall = { open = { 22, 80, 443 }, ping = true },
        },
    },

    -- Names players can use instead of IPs
    dns = {
        ['northbank.com'] = '82.103.40.12',
        ['www.northbank.com'] = '82.103.40.12',
    },
}

servers

Servers that are always on. They are added to every hack, and every machine can reach them, like the internet, unless their own firewall blocks it. Players can ssh into them, and what they change on them is saved for everyone.

  • servers?: table[]
    • Each server takes the same fields as a machine, plus:
    • website?: string or true
      • A folder in the resource with a static website, see Creating a Website. true gives an empty website to build in game.
  • The ip must be unique across the servers and the machines in your hacks.
  • A server with a website and no ports gets { 22, 80, 443 }. Without a firewall, every port is open to everyone.
  • A server can be the target of a hack.

dns

Names and the IP they point to. Used by the browser, curl, ping, ssh and every other command on every machine.

  • dns?: table<string, string>
    • [name] = ip. Names are not case sensitive.

A machine's own /etc/hosts is checked first, like on Linux. Add www. names separately if you want them to work.

Saved changes

What players change on the servers is saved in serverdata.json in the resource folder, kept apart from config.lua and websites/.

Replacing the resource folder on an update deletes serverdata.json. Keep a copy if players have built websites you want to keep. Delete it to reset every server.

Test commands

/hack and /hackterminal in server/commands.lua need the group.admin ace. Remove the file from server/main.lua to disable them, or change restricted.

HackConfig

A hack is described by a single table. The top-level fields describe the player's own machine plus a few game settings, and every machine in network uses the same machine fields.

Game

Only used at the top level.

  • target?: string or false
    • IP of the machine the player needs root access on. Defaults to the player's own machine. false = no target: the hack stays open until the player closes it.
  • attempts?: number
    • Wrong passwords allowed in total across ssh, rdp, su and sudo. Defaults to 3.
  • network?: HackMachine[]
    • The other machines. Machines without an ip are ignored.
  • commands?: table<string, function(source: number, args: string[])>
    • Your own terminal commands. They run on the server and return the lines to print (string[], a string or nil). See Creating a Hack Type.
commands = {
    whoowns = function(source, args)
        return ('%s belongs to Maria Holt'):format(args[1] or '?')
    end,
},

Machine

Used at the top level and in every entry of network.

  • ip?: string or string[]
    • The machine's IPs. More than one IP puts the machine on several networks. Defaults to '10.0.0.20' for the player's own machine.
  • host?: string
    • Hostname shown in the prompt, hostname and nmap. Defaults to 'pc'.
  • user?: string
    • The user the player logs in as. The home directory is /home/<user>. Defaults to 'user'.
  • password?: string
    • The user's password for ssh and rdp. Without it, no password is asked for.
  • rootPassword?: string
    • Root password for su and sudo. Without it, the player becomes root without a password.
  • desktop?: 'ubuntu' or 'kali' or 'chromeos' or 'mint' or 'fedora' or 'macos' or 'random'
    • Graphical desktop, see Desktops. CLI only without it.
  • ports?: number[]
    • Services the machine runs, e.g. 22 (ssh), 80 (http), 3306 (mysql), 5900 (remote desktop). Defaults to { 22 }, plus the remote desktop port when the machine has a desktop.
  • firewall?: table
    • See Firewall. No firewall without it.
  • processes?: string[]
    • Extra processes shown in ps aux, running as root.
  • files?: table<string, string>
    • Your own files as [path] = content, see Files.
  • locked?: string[]
    • Extra paths only root can read, e.g. { '~/secret.txt' }.
  • camera?: { coords: vector3, rotation?: vector3, fov?: number }
    • Makes the machine a camera in the world. The player opens it with view <ip> (port 554) and its password, and watches it live in a window. Pass plain tables ({ x, y, z }). A camera gets the ports { 80, 554 }. See LC CCTV.
  • onRoot?: function(source: number, machine: HackMachine)
    • Called on the server when the player gets root on this machine with the right password. Use it for rewards on machines that aren't the target.

Firewall

  • allow?: string[]
    • IPs that may do anything.
  • open?: number[]
    • Ports anyone may use.
  • ping?: boolean
    • Answer ping from anyone. Defaults to false.

firewall = {} blocks everything from the outside. See Networking for how traffic is checked.

Files

Every machine gets a full Linux filesystem of around 400 files and folders, built with its own user, host, IPs and OS: /etc with services (nginx, mysql, redis, systemd), logs in /var/log, a home with documents, projects, .git, browser data and scripts, /proc, /sys and the usual programs. Small things like documents and logs vary from machine to machine. Your files are added on top.

The OS follows the machine's desktop: /etc/os-release, the kernel, uname -a and the ssh banner say Kali, Fedora, Linux Mint, Debian (ChromeOS), macOS (Darwin) or Ubuntu. Machines without a desktop are Ubuntu servers.

  • ~ is the machine's home directory. Absolute paths work too.
  • Directories are created automatically.
  • Files starting with . are hidden and only shown with ls -a.
  • Using the same path as a default file replaces it, e.g. /etc/hosts or /opt/backup.sh.
  • Contents are plain text. Use \n for new lines.
  • Files in /var/www/html are the machine's website when it has port 80: curl and the browser app show them. See Creating a Website.
  • Image files (.png, .jpg, .svg, ...) are shown in the image viewer, see Images.

By default only root can read /root, /etc/shadow, /etc/gshadow, /etc/sudoers, /etc/sudoers.d, /etc/ssh/ssh_host_ed25519_key, /etc/mysql/debian.cnf, /var/lib/mysql, /var/spool/cron/crontabs, /var/log/auth.log, /var/backups/shadow.bak and ~/.ssh/id_rsa. A folder with a locked file in it can't be moved or copied without root.

The default files contain fake passwords to mislead players. Do not use these as real passwords:

    ip = '10.0.0.20',

Client

Hacks are always started by the server, see Server. The client can only check and close the terminal.

isOpen

Checks if the hack terminal is open.

exports.lc_hack:isOpen()

Return:

  • boolean - Returns true if the terminal is open, otherwise false.

Example

if exports.lc_hack:isOpen() then return end

close

Closes the terminal, like pressing Escape. A hack from a terminal is paused, a hack from startHack counts as a failure.

exports.lc_hack:close()

Server

All server exports take a HackConfig. They throw an error on invalid types, e.g. expected data.coords to have type 'vector3' (received nil).

createTerminal

Creates a new hack terminal in the world. With ox_target it becomes a sphere zone, otherwise an ox_lib point with [E].

exports.lc_hack:createTerminal(data)
  • data: table
    • coords?: vector3
      • Where the terminal is. Can be left out when screen is set: the terminal and its target zone are then placed on the screen.
    • config: HackConfig
    • name?: string
      • An optional name to refer to the terminal instead of using the id. Using the same name again replaces the old terminal.
    • label?: string
      • Text shown by ox_target or the [E] prompt. Defaults to 'Hack terminal'.
    • radius?: number
      • How close the player has to be. Defaults to 1.5, or half the screen's width when the terminal sits on a screen.
    • screen?: table
      • An in-world screen that shows the hacker's terminal to everyone nearby, see Screens.
      • coords: vector3
        • The center of the screen.
      • heading?: number
        • The heading of a player standing in front of the screen and looking at it. Defaults to 0.0.
      • width?: number
        • Width in meters. Defaults to 1.0.
      • height?: number
        • Height in meters. Defaults to width * 9 / 16.
      • distance?: number
        • How far away the screen is drawn. Defaults to 15.0.
    • onSuccess?: function(source: number, id: number | string)
      • Called when the player gets root on the target. id is the name if one was set.
    • onFail?: function(source: number, id: number | string)
      • Called on too many wrong passwords, when the player walks away from a closed terminal (see keepDistance) or drops.
    • keepDistance?: number
      • Closing the terminal pauses the hack: logins, files, history and attempts are kept, and the player continues where they left off when they use it again. The paused hack is discarded once the player is further away than this. Defaults to 10.0.
    • canUse?: function(source: number, id: number | string)
      • Called on the server before a player starts the hack. Return false and an optional message to stop them, e.g. for a missing item or a cooldown. The message is shown with an ox_lib notification.

Return:

  • id: number

Terminals are removed automatically when the resource that created them stops. Several players can use the same terminal at the same time, each in their own hack.

Example

exports.lc_hack:createTerminal({
    name = 'bank_server',
    coords = vec3(253.1, 228.4, 101.7),
    label = 'Use server',
    screen = {
        coords = vec3(252.4, 229.6, 102.4),
        heading = 340.0,
        width = 1.2,
    },
    config = {
        user = 'teller',
        desktop = 'macos',
        target = '10.1.0.10',
        network = {
            { ip = '10.1.0.10', host = 'bank-core', user = 'ops', password = 'Vault#2026', rootPassword = 'Valv-7781' },
        },
    },
    onSuccess = function(source, id)
        -- reward the player, open a door, etc.
    end,
    onFail = function(source, id)
        -- trigger an alarm, etc.
    end,
})

Adds a machine to the player's running hack, e.g. a device found with one of your commands. Its passwords stay on the server, like in a HackConfig.

registerGame

Registers a minigame with the core. Minigame resources call this once when they start and ship their own UI. The check function runs on the server for every guess, so the answer never has to leave the server. See Your own minigame.

exports.lc_hack:registerGame(name, data)
  • name: string
  • data: table
    • check: function(secret: any, guess: any): { correct: boolean, feedback?: any }
      • Compares a guess with the secret. feedback is sent back to the UI.

Registered games are removed when their resource stops. Register again on onResourceStart for lc_hack, since a restart of the core forgets them.

Example

exports.lc_hack:registerGame('pincode', {
    check = function(pin, guess)
        return { correct = guess == pin, feedback = #guess }
    end,
})

startGame

Starts a registered minigame for a player. The core counts attempts, enforces the time limit and calls cb when the game ends.

exports.lc_hack:startGame(source, name, options, cb)
  • source: number
  • name: string
  • options: table
    • secret: any
      • The answer. Stays on the server.
    • data?: table
      • Sent to the minigame UI.
    • attempts?: number
      • Wrong guesses allowed. Defaults to 3.
    • time?: number
      • Time limit in seconds.
  • cb?: function(success: boolean)

Return:

  • started: boolean - false if the player is busy (in a hack or another game) or the game isn't registered.

stopGame

Stops the player's minigame and closes its UI. Counts as a failure.

exports.lc_hack:stopGame(source)
  • source: number

isPlaying

Checks if a player is in a minigame.

exports.lc_hack:isPlaying(source)
  • source: number

Return:

  • boolean - Returns true if the player is in a minigame, otherwise false.

Events

lc_hack doesn't trigger events for other resources. Use the callbacks of the exports to react when a hack ends; they run on the server and can't be faked by a client.

Callbacks

CallbackFromCalled when
onSuccess(source, id)createTerminalThe player got root on the target.
onFail(source, id)createTerminalToo many wrong passwords, the player walked away from a paused terminal, dropped, or stopHack was called.
cb(success)startHackThe hack ended. Closing the window counts as a failure.
canUse(source, id)createTerminalA player is about to use the terminal. Return false, message to stop them.
onRoot(source, machine)a machineThe player got root on that machine.
commands[name](source, args)HackConfigThe player ran your command. Return the lines to print.
cb(success, ...)startGameThe minigame ended.

Errors in a callback are caught and printed, so they never break lc_hack.

exports.lc_hack:createTerminal({
    coords = vec3(253.1, 228.4, 101.7),
    config = config,
    onSuccess = function(source, id)
        TriggerEvent('my_heist:hacked', source, id) -- trigger your own event if you need one
    end,
})

Creating a Hack

A hack is a small puzzle. The player starts on their own machine, follows clues from machine to machine and wins with root on the target. This guide builds one from scratch: the player breaks into the CEO's laptop through an office network.

The finished config is at the bottom of the page.

Plan the path

Write the path down before any code, starting from the target and working backwards. Every step needs a clue the player can find on the machine before it.

#The player is onFindsWhich leads to
1workstation (own)A mail from IT about the intranetcurl intranet
2workstationThe intranet page, with a login in an HTML commentssh files@10.0.0.15
3fileserverA backup script with the CEO's passwordssh ceo@192.168.5.2
4ceo-laptop (target)The root password in .bash_historysu: the player wins

Three or four hops take most players 5 to 10 minutes. Keep the first clue easy to find, e.g. in /var/mail/<user> or on the desktop.

Create the player's own machine

The top level of the HackConfig is the machine the player starts on. Give it the first clue.

local config = {
    ip = '10.0.0.20',
    host = 'workstation',
    user = 'alex',
    desktop = 'macos',
    files = {
        ['/var/mail/alex'] = 'From: it@office.local\nSubject: New intranet\n\nThe intranet is up at http://intranet',
        ['/etc/hosts'] = '127.0.0.1\tlocalhost\n10.0.0.30\tintranet',
    },
}

/etc/hosts makes the name intranet work on this machine. Leave out desktop for a terminal only.

Add the other machines

Every machine in network has an IP, a user and the clue for the next step. password is asked for on ssh; it never leaves the server.

network = {
    {   -- The intranet: only a website, port 80
        ip = '10.0.0.30',
        host = 'intranet',
        ports = { 80 },
        files = {
            ['/var/www/html/index.html'] = '<h1>Office intranet</h1><!-- fileserver 10.0.0.15, user files / Arch1ve! -->',
        },
    },
    {   -- The file server sits on both networks, so the player hops through it
        ip = { '10.0.0.15', '192.168.5.10' },
        host = 'fileserver',
        user = 'files',
        password = 'Arch1ve!',
        files = {

Choose the target and attempts

Make the player work for it

Creating a Website

Websites live on servers from config.lua. They are always on, every player can open them in the browser app or with curl, and players can change them in game.

Add a server

Add a server with a website folder to config.lua.

servers = {
    {
        ip = '82.103.40.12',
        host = 'northbank-web',
        user = 'webadmin',
        password = 'N0rth!Web',
        website = 'websites/northbank',
    },
},

Give it a name

dns = {
    ['northbank.com'] = '82.103.40.12',
},

Create the website

Put the files in the folder. Loading starts at index.html, and every page, stylesheet and image it links to is loaded, up to 200 files.

websites/northbank/
    index.html
    about.html
    style.css
    img/logo.svg
    careers/index.html
<link rel="stylesheet" href="style.css">
<img src="img/logo.svg">
<a href="about.html">About us</a>
<a href="careers/">Careers</a>
  • Use relative links or links from the site's root (/about.html). A link to a folder opens its index.html.
  • Images can be .png, .jpg, .gif, .webp or .svg.
  • Pages that nothing links to are not loaded. A missing file prints a warning in the server console.

Open it

Restart lc_hack and open northbank.com in the browser app, or run curl northbank.com/about.html. In the browser test mode the website is loaded from the folder as well.

Static only

Websites are static: HTML, CSS and images. Scripts and forms never run, and a page can never load anything from outside, not even fonts or images from another site. That keeps players safe from pages other players made.

Building in game

Players change a website by logging in to the server and editing the files in /var/www/html, with the text editor, echo >, touch, mkdir, rm and mv.

ssh webadmin@northbank.com
mkdir /var/www/html/blog
echo "<h1>My blog</h1>" > /var/www/html/blog/index.html
  • The game server checks every change: the player must have logged in to the server in that hack. The server's user can write in its home, /tmp and /var/www/html; root everywhere.
  • Changes are saved and every other player in a hack sees them right away. They stay after a restart, see Saved changes.
  • website = true gives a server an empty website to build from scratch.
  • Limits: 100 KB per file, 500 files and folders written per server. Images can't be web addresses.

Websites in a hack

A website is a good first clue. Give a name to the server, let the player find the name in a mail, and hide the next step on the site:

  • An HTML comment: players who use curl see it, the browser hides it.
  • A page only linked from an HTML comment, e.g. <!-- <a href="admin.html">old admin</a> -->. It is loaded, but only players who read the source find it.
  • Staff names on an "about" page, used as usernames somewhere else.

Everything on a website can be read by every player. Hide hints there, never real secrets.

Creating a Hack Type

lc_hack is the core: the terminal, the desktops, machines, files and the server-side checks. Hack types are separate resources that build on it, e.g. hacking an ATM or the phones of people nearby. This guide shows the three building blocks, using LC Phonehack as the example.

Building blockWhat it does
commandsYour own terminal commands. They run on the server, in your resource.
addMachineAdds a machine to a running hack, e.g. a device a command found.
onRootCalled on the server when the player gets root on a machine. Give the reward here.
canUseDecides if a player may use a terminal, e.g. an item or a cooldown. LC Datahack uses it.

Add target = false for a hack without a goal: it stays open until the player closes it, so they can hack one device after the other.

Open a hack with your own commands

Start a hack from your resource, e.g. when a player uses an item. Every function in commands becomes a command in the terminal, with Tab completion and a line in help.

exports.lc_hack:startHack(source, {
    ip = '172.20.0.1',
    host = 'laptop',
    user = 'user',
    desktop = 'kali',
    target = false,
    commands = {
        scan = function(source, args)
            return { 'ID  DEVICE', '1   Phone-8c13' }
        end,
    },
})

A command gets the player and the words after it, and returns the lines to print: a table of strings, one string or nothing. Errors in it are caught and printed in the server console.

Add machines while the player hacks

Create a machine when the player finds something. It takes the same fields as a machine in a HackConfig, and its passwords stay on the server.

connect = function(source, args)
    exports.lc_hack:addMachine(source, {
        ip = '172.20.0.2', -- On the laptop's network, so the player can ssh to it
        host = 'Phone-8c13',
        user = 'mobile',
        rootPassword = '4821',
        files = { ['~/Notes/reminders.txt'] = 'New phone PIN: 4821' },
    })
    return 'Connected. Log in with: ssh mobile@172.20.0.2'
end,

Reward the player

onRoot runs on the server when the player becomes root on the machine with the right password. Check what you need again before you give anything: the player may have walked away.

onRoot = function(source, machine)
    exports.ox_inventory:AddItem(source, 'phone_data', 1)
end,

Validate everything on the server

  • Arguments come from the player. Check them: tonumber(args[1]), ranges, cooldowns.
  • Check the world on the server: does the NPC still exist, is the player close to it?
  • Give rewards in onRoot or callbacks, never because the client said so.

lc_phonehack

A complete hack type in two small files. The player opens a laptop, scan lists the phones of NPCs nearby, connect adds one as a machine, and the player finds the phone's PIN in its files and uses it with su.

  • Source and setup: LC Phonehack documentation and GitHub
  • Works with ox_inventory (an item opens the laptop and the reward is an item) and without it (a command and a callback).

Your own minigame

A minigame is a resource with its own UI that uses the core for server-side checks. This one asks for a 4-digit PIN and tells the player how many digits are right.

Server

local function register()
    exports.lc_hack:registerGame('pincode', {
        check = function(pin, guess)
            local right = 0
            for i = 1, #pin do
                if pin:sub(i, i) == tostring(guess):sub(i, i) then right = right + 1 end
            end
            return { correct = guess == pin, feedback = right }
        end,
    })
end

AddEventHandler('onResourceStart', function(resource)
    if resource == 'lc_hack' then register() end
end)

RegisterCommand('pincode', function(source)

    }, function(success)
        print(GetPlayerName(source), success and 'won' or 'lost')

end)

Networking

Machines are connected through simple /24 networks. Building a network is mostly about choosing IPs and firewalls so the player has to find the right path.

Rules

  • Two machines can only reach each other when they have an IP on the same /24 network (the first three numbers match, e.g. 10.0.0.x).
  • A machine with several IPs, e.g. { '10.0.0.12', '192.168.1.10' }, connects two networks. To reach 192.168.1.x, the player has to ssh into it first.
  • There is no routing. The servers from config.lua are the exception: every machine can reach them, like the internet.
  • Hostnames like db-server are looked up in /etc/hosts on the current machine, then in dns from config.lua. Replace /etc/hosts in a machine's files to make a name work in one hack.
  • arp remembers every machine the player tried to contact, even when a firewall blocked it.

Firewall

firewall = {
    allow = { '192.168.1.10' }, -- these IPs may do anything
    open = { 80 },              -- these ports are open to everyone
    ping = false,               -- answer ping from everyone
}
  • The IP that is checked is the player's IP on the same network as the target.
  • nmap shows blocked ports as filtered. A host that answers neither ping nor port 80/443 looks down, and nmap -Pn scans it anyway.
  • As root, the player can change a firewall with ufw disable, ufw allow 22 or ufw allow from <ip>. Changes last until the terminal closes.

Access

  • If the player's own machine has a desktop, the hack starts on it.
  • startx opens the desktop of the current machine.
  • rdp [user@]host opens a remote desktop on another machine. It needs port 5900, goes through the firewall and asks for the user's password, checked by the server.
  • The power button closes the desktop. If it was opened with rdp, it also logs off that machine.

A machine with a desktop and no ports gets { 22, 5900 }. When you set ports yourself, add 5900 if rdp should work.

Apps

  • Terminal - the real CLI in a window. Open it again for another terminal: each one has its own logins, folder and history, so the player can be on several machines at once. exit on the last login closes an extra terminal.
  • Files - browse the desktop machine's files, with Home, Desktop, Documents, Downloads, Pictures and / in the sidebar. Double click opens a folder, an image in the image viewer and anything else in the editor. Drag files onto a folder, another window or the desktop to move them. Locked files show a lock and an error dialog.
  • Text Editor - opens, edits and saves files. Save with the button or Ctrl+S. The path field decides where the file is saved; relative paths start in the home directory, and new files go to the desktop. Users can save in their home directory and /tmp, root everywhere.
  • Image viewer - shows the images in a folder with previous / next. Opened from the dock, it starts in ~/Pictures.
  • Browser - works like curl from the desktop's machine: same /etc/hosts, network and firewall. http://10.0.0.30/ shows /var/www/html/index.html on that machine, http://web01/notes.txt shows /var/www/html/notes.txt. Pages are sandboxed, scripts never run.
  • System monitor - the same processes as ps aux.
  • Cameras - every camera opened with view gets its own window, and several can be open at once. The one clicked last is live; the others freeze on their last picture with a timestamp (needs screenshot-basic). The game camera is turned and widened so the camera's view fits the window.

The desktop is ~/Desktop

The icons on the desktop are the files in ~/Desktop of the desktop's user. Anything saved or moved there (editor, echo >, touch, mv, drag and drop) shows up on the desktop right away, and files dragged onto the desktop are moved to ~/Desktop.

Images

An image is any file ending in .png, .jpg, .jpeg, .gif, .svg or .webp. What the file contains decides what is shown:

  • 'https://...' or 'data:image/...' - that image.
  • '<svg ...>...</svg>' - the SVG. Handy for hiding a hint in a picture, e.g. a sticky note with text.
  • Anything else - a landscape generated from the file name.

Windows can be moved by their title bar, minimized (the dock brings them back), maximized (or double click the title bar) and closed. The apps always use the desktop's machine, even after ssh-ing elsewhere in the terminal.

Screens

A terminal can have a screen in the world. While a player hacks the terminal, everyone near the screen sees the terminal and desktop in real time, using a Direct-Rendered UI (DUI).

Setup

Add screen to createTerminal.

exports.lc_hack:createTerminal({
    name = 'bank_server',
    coords = vec3(253.1, 228.4, 101.7),
    screen = {
        coords = vec3(252.4, 229.6, 102.4), -- the center of the screen
        heading = 340.0,                    -- your heading while looking at the screen
        width = 1.2,                        -- meters, the height follows 16:9
    },
    config = config,
})

The easiest way to find the values is to stand in front of the spot, look at it, and use your own coordinates and heading. /hackterminal does exactly that and places a screen 1.5 meters in front of you.

Leave out coords to put the terminal on the screen itself. Players then look at the screen and use it with ox_target (or [E] close to it) to start hacking.

exports.lc_hack:createTerminal({
    name = 'lobby_screen',
    screen = { coords = vec3(252.4, 229.6, 102.4), heading = 340.0, width = 1.6 },
    config = config,
})

The screen is a flat surface drawn in the world, so it can be placed on any wall, monitor or prop. It is meant to be seen from the front.

How it works

  1. When a hack starts from a terminal with a screen, the hacker's window is copied every time it changes, at most a few times per second.
  2. The copy is sent to the server with latent events, so large updates never block other network traffic.
  3. The server only accepts updates from the player hacking that terminal, and forwards them to players near the screen.
  4. Nearby clients run web/index.html?mirror as a DUI through lib.dui and draw it on the screen. The DUI is only created within distance and removed again when the player walks away.
  5. When the hack ends, the result stays on the screen for 5 seconds before it goes back to idle.

Security

  • The password field is always sent empty, so passwords typed by the hacker are never shown to anyone.
  • The HTML comes from another player, so the screen removes everything except the elements and attributes the terminal uses. Scripts, images, event handlers and url() in styles are dropped.
  • The server rejects updates larger than 100 KB and more than 10 updates per second from one player.

startxOpen the desktop of the current machine.
exit, logoutLog out: root to user, ssh back to the previous machine. On the player's own machine it closes the window, like Escape.

ssh with the wrong username, e.g. root@..., never works, like PermitRootLogin no.

Development

How lc_hack is put together, how to test changes without FiveM, and where to add your own commands, apps and desktops.

New client files must be listed in files in fxmanifest.lua, otherwise require can't find them.

Flow

  1. The player uses a terminal and the client triggers lc_hack:use. The server checks the distance and starts a session.
  2. The server sends the config without passwords with lc_hack:open.
  3. When the player submits a password, web/js/terminal/auth.js sends it through the NUI to client/terminal.lua and on to lc_hack:verify.
  4. The server checks it, counts attempts and decides the outcome. The answer goes back to the NUI.
  5. When the hack ends, the server calls onSuccess, onFail or the cb from startHack.

The events between client and server are listed in Events.

Testing in the browser

Run python3 -m http.server 8000 in the resource folder and open http://localhost:8000/web/. web/js/dev.js stands in for the client and server: it reads config.lua and the example in server/commands.lua, checks passwords like the server and keeps changes on the always-on servers in the browser. Add ?desktop=macos (or any desktop, random, none) to pick the desktop, and ?hack=../my_heist/hacks/office.lua to open your own hack, see Creating a Hack. In FiveM the file does nothing.

Adding a command

Commands live in web/js/terminal/commands/, one file per group. Add a function to commands; it receives the words after the command as a list and works with Tab automatically. Add it to help as well.

// web/js/terminal/commands/tools.js
Object.assign(commands, {
    // "whois 10.0.0.5" -> args = ['10.0.0.5']
    whois(args) {
        const m = findMachine(args[0]);
        print(m ? `${args[0]} is ${m.host}` : 'whois: unknown host');
    },
});

Adding a desktop app

An app is one file in web/js/desktop/apps/ plus a <script> line in web/index.html. It registers itself with its name and icon, and the name or icon per desktop where they differ. The dock shows apps in the order of the script lines. Icons are Font Awesome classes, styles go in web/css/desktop/apps.css.

// web/js/desktop/apps/calculator.js
registerApp('calculator', {
    open: openCalculator,
    name: 'Calculator', names: { kali: 'Galculator' },
    icon: 'fa-solid fa-calculator',
});

function openCalculator() {
    const body = el('div', 'calculator', '2 + 2 = 4');
    createWindow(appName('calculator'), body, { width: 260, height: 160, app: 'calculator' });
}

Adding a desktop

  1. Add an entry to THEMES in web/js/desktop/themes.js (its process, menu, names of Home, Trash and /).
  2. Add web/css/desktop/themes/<name>.css and a <link> to it in web/index.html. Copy an existing theme: it sets the colour variables, places .panel and .dock, styles the window buttons and the terminal (#term[data-os="<name>"]).
  3. Optional: a prompt in PROMPTS in web/js/terminal/prompt.js (bash is the default), and app names in the apps.

Default files and ports

  • Add default files in defaultFiles() in web/js/terminal/default-files.js. A path ending with / is an empty folder, and user, host and ips can be used in the text.
  • Lock a default file by adding its path to DEFAULT_LOCKED.
  • Name a port for nmap in SERVICES in web/js/terminal/state.js.

Limitations

  • No pipes (|). Redirection only works with echo.
  • Every hack is its own world: files written on a machine in a hack are gone when it ends. Only the servers from config.lua keep changes and share them.
  • grep works on a single file and is case-sensitive.
  • One desktop at a time. rdp to another machine closes the current one.
  • One hack per player at a time, and no cooldown on terminals.
